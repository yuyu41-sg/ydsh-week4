第4周实训周志

姓名：张宇　　学号：20230308059　　团队：ydsh-team　　项目：云购生活新零售数仓
本周主题：数据可视化与系统集成（Superset 仪表板、ECharts 数据大屏、Streamlit 智能问答、Docker 一键部署、查询优化与压测）

一、本周工作内容

1. Superset 可视化仪表板
- 部署 apache/superset 容器并接入数仓 Docker 网络，安装 Hive（pyhive）与 MySQL 驱动，注册双数据源并连通性验证
- 通过 REST API 一键创建 7 个数据集、6 个图表：全期KPI大数字（14.2M）、每日GMV折线、品类销售额柱状图、省份销售额条形图、支付方式漏斗图、门店TopN排行表，组装成"云购生活经营分析仪表板"
- 过程中踩了大量版本坑：Superset 6.1 新版默认构建移除了 echarts_pie/dist_bar 插件，逐个排查后改用漏斗图和 echarts_timeseries_bar；还发现图表类型存在 params JSON 与 viz_type 独立列两处存储，必须同步修改；排查过程全部沉淀为脚本注释，交付代码可一键复现
- MySQL 侧新建业务库 ydsh_ads，从 Hive ADS 层导出 7 张结果表并入库，作为大屏与 Superset 的 MySQL 数据源

2. ECharts 数据大屏
- 从 Hive 实查导出 7 组数据（月度趋势/品类/省份/时段×品类热力/支付方式/门店Top10/客单价×折扣散点）
- 开发 1920×1080 设计稿、scale 整体缩放自适应的暗色科技风大屏，含 KPI 卡片、折线柱状混合、品类柱状、省份热力地图（ECharts 官方标准 china.js，符合国家版图规范）、时段热力图、支付饼图、门店排行

3. Streamlit 智能问答应用
- 基于第3周 NL2SQL 后端搭建问答闭环：自然语言提问 → 大模型生成 SQL → 只读校验 → Hive 执行 → 表格+ECharts 图表渲染，支持历史对话、加载状态、错误提示与写操作拦截

4. Docker Compose 一键部署
- 编排 mysql / metastore / hive-server / superset / app 五服务，配置 depends_on 依赖链与 healthcheck 健康检查，密钥经 .env 注入；同时对 week1 的 compose 做了数据持久化加固（hive warehouse 改为命名卷），此后重建容器数据不丢失

5. 查询优化与压力测试
- 对比分区裁剪前后查询耗时（4.9s→4.4s），并诚实记录结论：模拟数据仅 1.5 万行，固定开销占主导，小数据集上优化重点在架构层；真实亿级数据下分区裁剪收益是数量级级别的
- 并发压测 10 并发×20 请求，全部成功，输出响应时间统计与优化建议报告

二、收获与体会

1. 版本意识比功能本身更重要：latest 镜像的 6.1.0 版本砍掉了不少图表插件，遇到报错先查版本变更，不能想当然
2. 排障方法论：前端报错不一定在前端——"invalid orderby" 的根因是后端存的 JSON 损坏；"不生效"的根因是数据库里有两处存储（params 与 viz_type 列）只改了一处。逐层验证（库内→API→前端）比反复试错高效
3. 数据持久化设计：容器可写层天然易失，有状态数据必须上卷；这次加固后重建容器数据不再丢失
4. 诚实的技术报告：压测数据不理想就如实写边界分析，反而比硬凑结论更有说服力

三、问题与解决

1. Superset 图表批量报 not registered → 确认 6.1 移除 echarts_pie/dist_bar，改用 funnel 与 echarts_timeseries_bar 替代
2. 图表参数改了但不生效 → 发现 slices.viz_type 独立列未同步，通过 ORM 直改数据库解决
3. KPI 大数字图要求时间轴列而 KPI 表无日期列 → 换用 big_number_total 类型
